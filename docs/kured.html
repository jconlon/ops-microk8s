Kured Memory Leak

Recurring goroutine hang in kured's reboot-check loop, plus stuck-reboot alerting — history, mitigations, and durable fixes · Updated 2026-08-29

Status: mitigated, not fixed. No kured release has resolved the underlying hang. A 64Mi memory safeguard plus a daily scheduled restart keep it from causing node memory pressure (issue #101). A separate Prometheus alert now covers stuck reboots/drains going undetected (issue #43) — see Prometheus Alert below.

The Symptom

Every kured pod runs a periodic reboot-check loop (--period=1h by default) that logs Reboot not required (or Reboot required) each cycle. At some point after pod start, the goroutine driving that loop dies silently on every pod simultaneously — same absolute-time window across all 8 nodes, regardless of when each pod started. The pod stays Ready, no error/warning logs, no pod events. Two consequences:

  • Reboot detection silently stops working — not just a display problem. A node needing a reboot after this point won't get one until the pod restarts.
  • Memory climbs unbounded from whatever the leaked state was, eventually OOMKilling the pod without the 64Mi limit (originally observed up to 14.6 GiB per pod on gold/trout).

Diagnose whether it's currently hung

# Last successful check per pod, compared to "now" — should be within
# the last ~1-2 hours (period=1h + some slack) if healthy:
for pod in $(kubectl get pods -n kube-system -l app.kubernetes.io/name=kured -o name); do
  echo "=== $pod ==="
  kubectl logs "$pod" -n kube-system --tail=200 | grep -E "Reboot (not )?required" | tail -1
done
date -u +"%Y-%m-%dT%H:%M:%SZ"   # compare against the timestamps above

# Memory usage — climbing toward 64Mi is a sign of an active hang
kubectl top pods -n kube-system -l app.kubernetes.io/name=kured

Current Mitigations

1. Memory limit (defense-in-depth)

kured-gitops/helm/kured-values.yaml sets a 64Mi memory limit / 16Mi request. This bounds the blast radius — the DaemonSet OOMKills and restarts a leaking pod long before it can pressure the node — but does not address the check loop silently dying, since a pod can sit well under 64Mi for a long time after its goroutine has already hung.

2. Scheduled rolling restart (durable mitigation)

A daily CronJob (kured-gitops/cronjob/kured-restart-cronjob.yaml) runs kubectl rollout restart daemonset/kured against a dedicated, narrowly-scoped kured-restarter ServiceAccount (RBAC limited to get/patch on the kured DaemonSet only — nothing else). This resets every pod's goroutines well inside the shortest hang interval observed so far (hours on 1.16.1, weeks on 1.22.0), independent of whichever kured version is deployed.

# Manually trigger a restart (e.g. to test, or if you suspect an active hang
# and don't want to wait for the 04:00 UTC schedule):
kubectl create job --from=cronjob/kured-restart kured-restart-manual -n kube-system
kubectl logs -n kube-system job/kured-restart-manual
kubectl delete job kured-restart-manual -n kube-system

# Check the CronJob itself
kubectl get cronjob kured-restart -n kube-system
kubectl get jobs -n kube-system -l job-name=kured-restart
Why a CronJob and not just a shorter reboot-check period? The hang is in kured's own goroutine, not the check interval — a shorter --period would just log more before hanging at the same point. Only a pod restart clears it.

Prometheus Alert — Stuck Reboots (Issue #43)

Separate from the memory leak above: issue #43 tracks a related gap from an earlier incident (#42) where a stuck drain on squid went undetected for days. kured-gitops/monitoring/kured-alerts.yaml adds a PodMonitor (kured has no Service — DaemonSet, metrics-only — so pods are scraped directly) and a PrometheusRule:

alert: KuredRebootStuck
expr:  kured_reboot_required == 1
for:   48h

kured_reboot_required is a gauge kured already exposes on :8080/metrics (one series per node). Fires if a node has needed a reboot continuously for 48h — two full reboot-window cycles (02:00–06:00 America/New_York, checked hourly per kured-values.yaml) — which gives real margin above the ~20h a node can legitimately wait if it needs a reboot just after the window closes for the night.

Why this metric and not the reboot-in-progress annotation

Kured also sets a weave.works/kured-reboot-in-progress node annotation (annotateNodes: true) when a drain starts — a more semantically precise signal in theory ("actively draining" vs. "just needs a reboot"). Not used, for two reasons found while evaluating it:

  • Prometheus can't read node annotations directly. Exposing one requires adding --metric-annotations-allowlist=nodes=[weave.works/kured-reboot-in-progress] to kube-state-metrics — a shared, cluster-wide monitoring component, not something scoped to kured alone.
  • Live evidence the annotation isn't trustworthy: trout carried a stale weave.works/kured-reboot-in-progress: 2026-07-31T06:16:13Z annotation for a full month after that reboot cycle completed successfully (kured_reboot_required on trout was confirmed 0 the whole time). Kured doesn't reliably clear this annotation on success, so alerting on its presence would need cross-checking against kured_reboot_required anyway — at which point the metric alone is sufficient.

Once this alert fires, see Alerting & Notifications for how it actually reaches you (desktop notification on mullet, not just the Alertmanager UI).

Not yet tested end-to-end. The rule is confirmed loaded (health: ok) and all 8 nodes are being scraped successfully, but the alert has not been fired against a real reboot-pending node — doing so would mean creating a genuine /var/run/reboot-required sentinel (or waiting out a real 48h stuck drain). Verify manually the next time a node has a legitimately long-pending reboot. 
# Confirm the rule is loaded and healthy
kubectl get prometheusrule kured-alerts -n monitoring
# Or query Prometheus directly:

# Confirm all 8 nodes are being scraped
kubectl get podmonitor kured -n kube-system

Incident History

Discovered Nodes swapping — pods at up to 14.6 GiB 2026-06-06

Mullet found swapping. kured-wc4ck (gold) and kured-bknv4 (trout) each at 14.6 GiB; whale, mullet, tuna also elevated (2.9–5.3 GiB) against a normal baseline of ~10 MB. Version at the time: kured 1.16.1 (chart 5.5.1), no memory limits set. Immediate mitigation: deleted all 8 pods to free memory.

Root-caused Goroutine leak traced to upstream #1015, fixed in 1.16.2+ 2026-06-07

A 64Mi memory limit was added first as an interim safeguard. Deeper investigation of pod logs across all 8 nodes found every instance's periodic check stopped logging within the same ~40-minute absolute-time window (09:00–09:40 UTC) regardless of pod start time — a synchronized hang, not organic per-node drift. No correlated cluster event found; the trigger is internal to kured. This matched upstream's kured 1.16.2 changelog: "Fix goroutine leak by @evrardjp in #1015". Latest stable at the time was 1.22.0.

Upgraded chart 5.5.1 → 5.12.0 (kured 1.22.0). Baseline memory dropped from 38–48 MiB (climbing) to 8–11 MiB flat — a strong early signal, pending confirmation the check loop survived longer than 1.16.1's few-hour hang window.

Recurred Same hang signature on 1.22.0, after 53 days 2026-07-30

All 8 pods stopped logging checks simultaneously in a single window, ~10 hours of silence at time of discovery. Memory 14–51 MiB — under the 64Mi limit, not yet OOMKilled, but the check loop was dead. The 1.16.2 upstream fix reduced frequency (hours → 53 days) but did not eliminate the underlying bug. Immediate mitigation: restarted all 8 pods again. Latest upstream at the time: 1.23.0 (2026-06-30), changelog not yet checked.

Recurred Same hang after 29 days — no upstream fix found, durable mitigation added 2026-08-29

All 8 pods again stopped logging checks in the same narrow window (09:08–09:53 UTC), ~8 hours of silence at discovery — an even shorter interval than the previous cycle (29 vs. 53 days), suggesting this is not a fixed period, just recurring. Checked kured 1.22.1 and 1.23.0 changelogs: both are pure dependency/CI bumps, no goroutine/memory/reboot-loop related changes. No further version to chase.

Immediate mitigation: restarted all 8 pods. Durable mitigation: added the daily kured-restart CronJob described above, so this stops requiring manual intervention regardless of kured version going forward.
