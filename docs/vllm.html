What It Is

vLLM is a self-hosted, OpenAI-API-compatible LLM inference server. It runs one model (Qwen/Qwen2.5-7B-Instruct-AWQ) on the cluster's only GPU — an RTX 2000 Ada in whale — so anything on the LAN that speaks the OpenAI chat-completions API can get local LLM inference without calling out to an external provider. It was a net-new addition (issue tracking: see the vLLM app in ArgoCD) — never had a Caddy entry or prior hostname, unlike most other services in this cluster which migrated from Caddy to kgateway.

Why self-hosted

  • No per-token cost or external API dependency for cluster-internal tooling
  • Data stays on the LAN — relevant for anything processing local/private content
  • A real (if modest) GPU workload to justify and exercise the GPU Operator / NVIDIA device plugin setup

Architecture

Client — OpenAI API request —▶ vllm-router (mullet) — routes to engine —▶ vllm-qwen25-7b engine (whale, GPU)

Deployed via the vllm-project/production-stack Helm chart (vllm-gitops/helm/vllm-values.yaml), managed by ArgoCD like everything else in this cluster. Two components:

  • Router (vllm-deployment-router, runs on mullet) — the stable entry point; handles routing to model-serving engines. Chart default resources (1000Mi request/limit) crash-looped with a bare SIGKILL on every cold start after a 2026-07-26 whale reboot — no OOMKilled reason or kernel OOM evidence found, so the exact mechanism is unconfirmed, but raising the memory limit to 1536Mi (request 512Mi) was the standard low-risk mitigation and resolved it.
  • Serving engine (vllm-qwen25-7b-deployment-vllm, runs on whale) — the actual model process, GPU-bound via nodeSelectorTerms: gpu-class=rtx2000-ada and runtimeClassName: nvidia. Pinned to whale because it's the only node with a GPU.

VRAM budget: ~4 GiB model weights + ~9 GiB KV cache headroom, within the 16 GB card at 85% utilization.

16 GB VRAM ceiling — not being upgraded. The RTX 2000 Ada caps out around a 14B-parameter INT4 model; the current 7B model has plenty of headroom under that. A GPU upgrade for whale was evaluated in issue #71 (RTX 4500/6000 Ada options, pricing, a Tesla V100 dual-GPU approach) and closed without action — no current need, and whale's PSU wattage is unknown via DMI, a real risk for the higher-TDP cards. If a larger model is ever needed, issue #100 (a dedicated rackmount GPU node replacing tuna) is the preferred path over upgrading whale in place.

Why a 7B model, not something bigger

O'Reilly Radar — "When Smaller Models Win" (2026) argues that task-specific small models (NVIDIA's own cutoff: under 10B parameters) consistently beat general large models once a problem is well-defined and narrow — "start large" only applies while the problem itself is still being figured out. That maps directly onto this deployment:

  • Qwen2.5-7B-Instruct-AWQ is already well inside the article's "small model" range.
  • Its actual production use — freshrss-streams summarizing extracted article text into structured fields — is exactly the narrow, stable, already-defined task type the article says small models excel at, not an open-ended problem that would justify a bigger general model.
  • It retroactively explains part of why kagent struggled: open-ended agentic tool-use is a broad, loosely-defined task — the opposite of what a small quantized model is suited for. That's a reason it was disabled, not a reason to size up the base model for a use case that no longer runs.
The right lever if summarization quality ever needs improvement: LoRA fine-tuning the current 7B model on freshrss's own examples — the article's own recommended "transition to specialized" step — not swapping to a bigger general-purpose model. It fits the existing 16 GB card, keeps cost and latency down, and is more targeted than raw size. Nothing today indicates this is needed; noting it here as the first thing to reach for, ahead of a model or GPU upgrade, if it ever is.

No API key required on the local network.

# List available models
curl http://192.168.0.218/v1/models | jq .

# Health check
curl http://192.168.0.218/health

# Chat completion
curl http://192.168.0.218/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2.5-7B-Instruct-AWQ",
    "messages": [{"role": "user", "content": "What is the capital of France?"}],
    "max_tokens": 100,
    "temperature": 0.7
  }' | jq .choices[0].message.content
# Python (OpenAI SDK) — base_url is the only thing that changes
from openai import OpenAI
client = OpenAI(base_url="http://192.168.0.218/v1", api_key="none")
response = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct-AWQ",
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)
print(response.choices[0].message.content)

freshrss-streams (part of the freshrss enrichment pipeline) is an active production consumer — not manual/ad hoc. It calls this vLLM instance's OpenAI-compatible chat-completions API at http://192.168.0.218 with model Qwen/Qwen2.5-7B-Instruct-AWQ to summarise extracted article text (Boilerpipe-extracted, per-entry) into the pipeline's summary / vi_summary_bullets output fields. Bounded to THREAD_POOL_SIZE=2 concurrent in-flight requests via a bounded ExecutorService, with a 120s per-call timeout (failures recorded as vi_summary_status=failed, never fed back as stream errors). Full detail, including the consumer's config table and failure/observability semantics: freshrss's architecture.html#vllm-integration.

kagent, a Kubernetes-native AI agent framework, was deployed (issue #111) with a real ModelConfig pointed at this vLLM instance's internal endpoint — --enable-auto-tool-choice and the Hermes tool-call parser are configured on vLLM specifically for this (Qwen2.5's tokenizer already includes Hermes-style tool-call templating, so no custom chat template was needed). It worked: verified end-to-end, including a real agent session completing a full agent → ModelConfig → secret resolution chain with no errors.

It was then deliberately disabled after a follow-up evaluation (issue #112) found it added nothing over using Claude Code directly — every request round-tripped through the quantized 8192-token vLLM model (slower than a full-size model), the web UI was clumsy next to a Claude Code session, and kagent had no event-driven behavior of its own (no AlertManager receiver, no Argo Events sensor, nothing watching anything — it was pure request/response, same shape as talking to Claude Code except slower). The useful domain knowledge from its bundled agents was extracted into this repo's Claude Code project skills (.claude/skills/{k8s-troubleshoot,kgateway,promql,observability}/SKILL.md) before disabling.

Initially just disabled (controller/UI/tools/agents torn down, CRDs and database kept for a possible re-enable) — later taken to full removal: the git manifests (kagent-gitops/, argoCD-apps/kagent*.yaml) were removed first, which broke the still-running kagent-database ArgoCD app (its source path vanished out from under it, producing a ComparisonError). Cleaning that up surfaced the rest of the half-finished disable, so the remaining pieces were removed too: the kagent-crds/kagent-database ArgoCD apps, the kagent CRDs (deleted manually — a Helm chart crds/ directory, not covered by cascade delete), the retained CNPG database and role (~9.3MB, just kagent's own session/tool-config state — set ensure: absent declaratively for the role, though it had to be dropped manually via psql too, since CNPG never tracked it as reconciled in the first place — same class of bug noted in #111's original deployment history), the kagent namespace, the kagent-httproute.yaml/kagent-certificate.yaml manifests and the Gateway's https-kagent listener (kagent.verticon.com was never publicly usable without these anyway), the kagent-mcp Grafana service account, and teller/.teller-kagent.yml. The vLLM tool-calling flags above (--enable-auto-tool-choice, Hermes parser) were left as-is — harmless with no consumer, and cheap to re-add support for later if needed. The 4 extracted Claude Code skills remain, with no dependency on any of this.
