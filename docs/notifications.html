Alerting & Notifications

How a firing Prometheus alert actually reaches someone — desktop notifications on mullet · Updated 2026-08-29

Before 2026-08-29, no alert notified anyone. Alertmanager routed everything to a "null" receiver — alerts only existed if someone opened alertmanager.verticon.com and looked. Issues #79 and #43 both trace back to real incidents that went unnoticed for hours-to-days as a direct result.
Delivery
notify-send
Desktop popup on mullet, jconlon's login session
Poll interval
5 min
systemd --user timer
Dedup
Fingerprint
Notifies once per alert, once more on resolve

Pipeline

Prometheus — rule evaluates true, for: duration elapses —▶ Alertmanager — polled every 5m —▶ ops alertmanager notify — new/resolved only —▶ notify-send

scripts/alertmanager.nu (ops alertmanager notify) queries GET https://alertmanager.verticon.com/api/v2/alerts?active=true&silenced=false&inhibited=false, drops the always-firing Watchdog heartbeat alert, and diffs the result against ~/.cache/ops-microk8s/alertmanager-notified.json — a list of previously-seen fingerprints — so a still-firing alert only pops once, not every 5 minutes. A separate low-urgency notification fires when a previously-tracked alert drops out of the active list (resolved).

Run via a systemd --user timer, not a system unit — installation and management commands are in scripts/systemd/README.md's Alertmanager Desktop Notifications section. The key reason for --user: notify-send needs the logged-in desktop session's D-Bus bus, which a system-level unit doesn't have without extra plumbing.

# Manually check right now
ops alertmanager notify

# Force re-notification of everything currently active
rm ~/.cache/ops-microk8s/alertmanager-notified.json
ops alertmanager notify

# Timer status
systemctl --user status alertmanager-notify.timer
journalctl --user -u alertmanager-notify.service -f

Why notify-send, not PagerDuty

Issue #79 originally proposed full PagerDuty integration — a dedicated on-call paging service with phone/SMS escalation, severity-tiered routing, and an integration key managed via Teller/Google Secret Manager. None of that was built. notify-send was chosen instead because:

  • This is a single-admin home lab, not a team with on-call rotations — PagerDuty's escalation policies and paging infrastructure solve a coordination problem this cluster doesn't have.
  • Zero new external accounts, secrets, or paid services — just a script and a systemd timer, both already fully within this repo's existing tooling (nushell, devbox, systemd).
  • notify-send is good enough for the actual failure mode both #79 and #43 describe: an alert firing silently with nobody looking. It directly closes that gap.
The real limitation this doesn't solve: notify-send only reaches you while logged into mullet's desktop session. If you're away — traveling, or mullet's screen is locked/logged out — you'll miss it entirely, exactly the scenario PagerDuty's phone paging exists for. If that ever becomes a real problem, email (Alertmanager's built-in email_configs receiver) or a chat webhook (Slack/Discord) would reach you anywhere with much less setup than PagerDuty — see the options discussion in #79.

Both are picked up automatically — the notify script doesn't need per-alert configuration, it reacts to anything Alertmanager reports as active (minus Watchdog).

Known Limitations

  • Desktop-session only. No reach while away from mullet or logged out — see the callout above.
  • Not end-to-end fire-tested. KuredRebootStuck is confirmed loaded and healthy in Prometheus, and the notify pipeline is confirmed working (tested with a synthetic tracked-alert resolve), but no real alert has fired through the whole chain yet. Worth confirming next time any cluster alert genuinely fires.
  • 5-minute polling means up to a 5-minute delay between an alert going active/resolving and the notification appearing — acceptable for the current alert set, which all use for: windows measured in hours.
